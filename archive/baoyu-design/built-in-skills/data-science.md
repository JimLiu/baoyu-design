name: "data-science"
description: "Data science\nInvestigate product metrics and paint them onto the product when a screen can show them"
---
The user wants to understand what's actually going on with their product — how it's used, where it leaks, which opportunities are worth pursuing — and, when there's a screen to show it on, to see those numbers painted onto the product itself rather than trapped in a spreadsheet. You're running that workflow end to end: grounded investigation first, display when it helps. The research stands on code and queries; the overlay is one way to present what you find, not a prerequisite for finding it.

Start by interviewing the user briefly, because the inputs vary and the north star is theirs to name. Ask who uses this product and what a successful session looks like for them; what metric they'd move if they could move one; what date range matters; and what they're specifically hoping to learn, worried about, or already have a hunch on. Ask what they can give you: the minimum is the product's source code (connect the repo via GitHub) and a way to query its analytics — code plus metrics is enough to ground every claim. The work gets much better with a feedback export and any survey or support dump they have on top. Read the source to find where telemetry is emitted — the event names, the properties they carry, which component fires each one — and that inventory is your map of what's measurable. Then ask the user to connect an MCP to whatever analytics store those events land in (BigQuery, Snowflake, Amplitude, whatever the code points at) if it isn't already connected, and pull the numbers yourself. Don't proceed on placeholder numbers; if the connector won't connect, say so and mark what's blocked.

Before touching any input, stand up a kanban as your workplan and keep it current the whole way through — it's how the user follows what you've done and what's left, and it's how you keep yourself honest about which claims are checked. Write a `kanban-data.js` that sets `window.__kanban = {updated, columns:[{id:'todo'|'doing'|'review'|'done', label}], tags:{<tag>:{label,color}, …} for the card kinds you'll use (research, synthesis, idea, artifact, infra), cards:[{id,col,tag,title,notes,links?}]}` and a simple `Kanban.dc.html` artboard that renders it. Seed it with one card per input you're about to read, one per synthesis step, and an artifact card for the findings file. Every time you finish a piece of reading or analysis, move the card and rewrite its `notes` with what you actually found (numbers, not adjectives); every time an analysis raises a new question, add a card for it. The board is the visible trail of the work, and it stays in the project when you're done.

Read each input on its own terms. A feedback export is read for themes, sentiment, verbatim quotes that make a theme concrete, and explicit feature asks — tally the themes as shares of the total so "reliability 32%" means something, and keep the quotes attributed so a finding can carry one. Metrics are read by going back to the telemetry inventory you built from the code and querying each event directly: per-day distinct users, which screens and elements fire which events, what's instrumented and — just as important — what isn't (a control with no event behind it is a gap to report, not a zero to reason from). The source repo grounds all of it: what a button is wired to do and which events it actually fires is the ground truth, and reading the component behind any number you're about to lean on is how you catch a stale mapping before it misleads you.

Then go one level deeper than the inputs hand you. Define the outcome the user named (their north star, or a proxy like "reached the success event the user named — a checkout, a publish, a return visit"), partition the population into reached-it versus didn't, and compare the two groups on every behaviour and attribute you can query — entry path, session length, whether they hit an error, plan tier or whatever segment dimension this product has. Compute per-element derived metrics — "of sessions that touched this element, % that reached the outcome" turns "what's popular" into "what predicts success". That anchored analysis tells you where to dig first; the interesting findings are often the ones nobody thought to ask for, so also run an exploratory pass: look for surprising segments, behaviours, and correlations the user didn't name — big differences between cohorts, features whose usage pattern doesn't match their prominence, cliffs in retention or session length, outliers in either direction — because the goal is finding insights that lead to design opportunities, not just confirming one metric. When any comparison throws up a surprising number, drill it to the ground before you lean on it: pull the sub-population, look at what those sessions actually did (opened? deleted? came back? went elsewhere?), split by who they are (first-timers vs returning, which plan or segment, which entry path), and keep going until the number has an explanation rather than just a value.

Every one of those comparisons will hand you gaps that look like levers, and almost all of them are inflated. When you find that users who did X reached the outcome twice as often, treat that number as an upper bound on what X could possibly cause, not as a measurement of it — the people who did X are the people who arrived with intent, and intent drives both sides of the correlation. Ever-did-X versus ever-reached-Y cuts carry a second inflation on top: sessions that live longer accumulate both, so the gap partly measures lifetime. Before you quote a gap, stress it: stratify by an engagement measure and by entry path, compare within a single account where the data allows it, and read the gradient — a gap that shrinks as engagement rises is selection talking, because among sessions that are clearly being worked on, the behaviour stops predicting much. Then report the raw gap together with what survived: "raw fourteen points, about eleven under any single control, six among the most engaged" is an honest sentence, and the raw number alone is not.

Be adversarial with yourself before you're done. For every finding that would change a decision, re-verify it against the source code and a fresh query: read the component that supposedly fires the event and confirm it does; check whether a field you're filtering on is populated by the client event or a separate server event you need to join; check whether a count you're treating as "users did X" includes mechanical rows (bot or automation traffic, retries, system-generated rows) that inflate it — and before you lean on any column as a record of what a user chose to do, make it pass one diagnostic it can't fake: query a population whose definition forbids the value (a "has attachments" count should be near zero among sessions that qualified for a nothing-attached prompt; if it reads ninety-nine percent, the column is counting something mechanical that rides on every row) and check what fraction of rows carry the join key you're about to join on, because a key that's empty on half the rows drops them silently and the result still looks plausible. When a re-check overturns something, correct it everywhere — the kanban card, the data file's header comment, and any downstream analysis that cited it — and write the correction as a correction so a future reader knows the old number existed. When you're about to explain a gap away as composition — "the no-X group is mostly throwaway sessions" — do the two lines of arithmetic instead of the judgment call: reweight the group table you already have, assuming zero within-group difference, and see how many points composition actually reproduces; sometimes it is most of the gap and sometimes it is a tenth of it, and you don't know which until you compute it on numbers already in front of you. And for the few numbers that will change a decision, being adversarial with yourself is not enough, because frame errors survive their author's re-reading — the author re-checks inside the same frame that produced them. Have someone who didn't compute the number try to kill it from the saved artifacts before it ships; the errors that catches are precisely the ones you cannot see. A surprising number that survives this treatment is a finding; one that doesn't was a bug in your understanding, and catching it here is the whole point.

Synthesis turns readings into findings and findings into ranked opportunities. Write the jobs-to-be-done and the personas that fall out of the feedback and the cohort splits — who is this product for, and what are they hiring it to do. Write a works/broken map: one row per surface, what the data says is working and what's leaking, cross-referencing the feedback theme against the metric. Then rank the opportunities against the user's north star on something like reach × pain × confidence, and sort them into fixes (things that are broken and we know how to fix), builds (things people are asking for that we'd ship), and bets (things the data suggests but we'd need to test).

The findings document, `findings.html`, is written to be read — a stakeholder should be able to open it cold and understand what you found and why it matters. Lay it out as a readable page: the north star and the inputs you worked from at the top; the personas with their jobs-to-be-done; the works/broken map by surface; then each finding as a short section (the observation in plain English, the evidence with its query and date, who it affects, and the so-what); and finally the ranked opportunities — each one tagged fix/build/bet, naming the findings that support it and the metric that would confirm it, scored on reach × pain × confidence. Carry the same content as structured data in a `<script type="application/json" id="__findings">` block inside the page — `{asOf, northStar, inputs, personas:[{id,name,jtbd,evidence}], surfaces:[{name,works,broken,theme,metric}], findings:[{id,observation,evidence:{query?,source?,asOf},affects,soWhat}], opportunities:[{id,kind:'fix'|'build'|'bet',hypothesis,findings:[ids],metric,reach,pain,confidence}], gaps:[…]}` — so a later step (an experiment brief, a story page) can consume it without re-parsing the prose. If the document already exists from an earlier run, update it in place rather than starting over — keep ids stable and mark corrected entries as corrected. When there's no product screen in the project, stop there — the findings document is the deliverable, and the user may just want to read what you found and decide for themselves.

When a question lands on a screen that's already wired, or the user returns days later with a follow-up, re-read your own artifacts first — the telemetry map, the views and their `asOf` dates, the findings — answer from what's there citing the as-of, and query fresh only when the question actually needs it; update artifacts in place (append views, mark corrected findings corrected) rather than starting over. When the project has a product screen that isn't wired yet — a prototype or template the numbers are about — offer to paint the findings onto it with the data overlay. The overlay is the presentation layer, not the research: every number it shows should already exist in your analysis, with a query behind it. Wire it on demand, as a step, when the user wants it: give every element a product question might be asked about a short, stable `data-metric-id` (kebab-case, readable: `copy-link`, `tab-export`; leave decoratives untagged — or pass the template's own stable attribute via `id-attr` if it already carries one), `copy_starter_component({kind: "data_overlay.js"})` into the project (its output carries the load-order snippet — on a plain page, a `<script src="data-overlay.js">` tag before the wrapper), wrap the screen in `<data-overlay src="./overlay-data.js">`, and expose it as an on-by-default tweak that maps the `src` attribute (src present = on, absent = off; with no src the overlay is a true passthrough). Set `controls="on"` when the user should explore between views; leave controls off for a story page or deck slide that pins one view programmatically. Also load the data file with a plain `<script src="./overlay-data.js">` before the component: the standalone-export bundler only discovers resources referenced in standard HTML attributes, so that tag is what embeds the data into exports (the component falls back to the pre-set global when its own fetch can't resolve). Before calling the display done, verify it: tweak on paints correctly (no hatched squares where values exist), tweak off is a true passthrough, and the markup, data file, and telemetry map cross-read — every tagged id has a row and a map entry, every event the map names exists in the source; a story page additionally reads cold, with its numbers matching its file. Alongside the data file, keep a telemetry map — `telemetry-map.md` next to `overlay-data.js` — that names the analytics source, lists each tagged id with its event and disambiguating fields, names the funnel-top event counts can be sanity-checked against, lists what is NOT instrumented and known staleness (events that only started on a date, gated elements, double-fires), and closes with how to re-query. Views are self-describing for display; the map is what makes refresh turns and gap answers fast without re-deriving the wiring every time. Keep it freeform and read it on demand — don't paste it into conversation wholesale. If no analytics connector is live yet, wire the tags and the telemetry map but hold the views file until real numbers exist — a placeholder painted on a product screen gets read as real. The overlay shows its honest empty state with the ask button as the designed path forward; say what's blocked and fill the views the moment the connector connects.

The component ships zero built-in view types: you author every view, and the component just paints what's there. The file sets `window.__overlays = {views:[…]}`; each view is one thing you want someone to see. Give it a short identifier-like `id` ([A-Za-z0-9_.-]), a `label`, a `sentence` ({metric, cohort, window} — the plain-words phrases the sentence control shows, each ≤64 chars of ordinary text), a `basis` (the denominator in plain words — "all workspace users active in the window"; required on any view whose elements carry values, and the component paints a visible warning if you forget it), a `source` (the query recipe, written precisely enough that a later refresh can re-run it without guessing — table, filter, the COUNT DISTINCT column, the window), an `asOf`, a `meta` ({range, n, unit, about} — the data's own date range, the volume the query returned with a unit naming the exact thing counted ("card-open events", never a vague "events"), and `about`: a short plain-words description of the exact data cut, under 100 characters, saying for a derived metric what counts as one — it renders as the trust subtitle under the sentence row when controls are on, and the legend drops whatever text the subtitle replaces), and `refreshable: true` when re-running that source makes sense. Then the elements: a `value` paints a colour wash and tag into the view's `spectrum` (single-hue sequential, or three colours with a `baseline` for diverging; `good:'low'` when lower is better); `value: null` means measured-and-found-nothing and renders hatched — visibly different from a low number; no value at all is a spotlight; a `callout` ({head, body}) pins an auto-numbered annotation card; a `delta` paints a change arrow, but only when the view declares `deltaBasis` — a delta without a stated comparison is a number without meaning. A `finding` line on the view renders as the story's lead line above the stage — the first thing the user reads, so write it from the computed numbers after you have them, not before. Keep ids under 64 characters — the refresh round-trip drops longer ones. Author the views the project's questions need — a usage picture, a cohort comparison as two views, a story view that spotlights and annotates without numbers — and when you author a primary metric view, seed it across the standard windows (last 24 hours, last week, last 4 weeks) as sibling views so the sentence control's window switches stay instant; custom ranges go through the ask-Claude turn.

When the work is a redesign, use the views' numbers to drive it, not just annotate it: rank what people actually reach, find the drop-off, and frame each proposed variation as a hypothesis naming the metric that would confirm it — "moving X above the fold should raise its reach from ~N% to ~M%". When two directions are both plausible and the data doesn't pick a winner, say so and suggest testing them with the experiment workflow. When a question the data can't answer would change the design, propose the missing event as a thing to instrument.

Telling one finding as a story is the same vocabulary, used sparingly: one view, a handful of elements painted or spotlit, callouts that reference a three-beat narrative — the insight (the observation with its number, readable cold), the implication (why it matters), and what to test (a hypothesis with the metric that would confirm it; every story ends with what to test). For a share-ready artifact, put the story on its own standalone page that wraps a copy of the screen headless (`controls` off, the view pinned — `view` is a property, not an attribute, so either set it with one script line or make the story view the only view in that page's file) with the narrative laid out beside it, and keep its data file separate from the project's main one. When a finding came from `findings.html`, carry the finding id on the view so the chain from research to picture stays traceable. A flat metric is only interesting relative to what the data could have detected — when the story is "no change", say what size of change would have been visible.

When the user clicks "Ask Claude to fetch metrics" in the overlay, that request arrives in chat as a plain ask. A refresh names a view: re-run that view's recorded `source` for the same population and window, re-anchored to today; rewrite the view in place with fresh values, a new `asOf`, recomputed `meta`, and an updated `finding` the fresh numbers support; leave every other view untouched. A missing combination names the metric, cohort, and window the user picked: compute it for real, append a new view with its own sentence, basis, source, and asOf, and the overlay adopts it when the file reloads. If there are no views yet, author the first one the same way. In every case the numbers come from the analytics source — if the connector is gone or errors, say so in chat and leave the file alone; the overlay shows its stale state honestly, and an invented number painted on a product screen gets acted on as if it were real. If the request is genuinely unanswerable (no such event, a cohort the data can't express), say that too — don't write a fake view.

When a question is about a path — "how many people make it from create to share?" — compute the funnel in your analysis and present it in the findings or the chat as an ordinary chart; the overlay carries element views only. Compute funnels strict-sequentially: per user, match step 0's first occurrence in the window, then each later step's first occurrence at or after the prior matched step — never each event's independent first-in-window occurrence, which undercounts whenever a later step's event is common — and always show the starting population as the visible denominator. When the user asks about a hatched element, re-check the analytics source before filing it as a gap — events often exist under a different name than was guessed; fix the ones you find (set the real event, refresh the value) and for the confirmed rest write `telemetry-gaps.md` next to the data file: element, label, proposed event name and properties — a handoff list the user takes to their product codebase (you can't instrument their product from here). Offer to refresh once the events ship. If the project carries files from the older overlay components (a `metrics-data.js` snapshot, a `window.__insights` file, a `<metrics-overlay>` or `<insight-overlay>` wrapper), recognize them and say so: they keep rendering as they are, but their round-trip buttons are retired. Offer to rebuild the data as views on the data overlay — the element tags carry over unchanged, so it's a wrapper and data-file swap — and read the old sidecar (`metrics.skill.md`) for its event map the way you'd read `telemetry-map.md`; never silently edit or delete the old files; leave them until the user says remove them.

Treat every number with the same care you'd want from a colleague. Cite the query behind any figure a decision rests on, date every claim (a view was true on its `asOf`, not today), and never invent a number — if the connector returns an error or a table is empty, say so and mark the card blocked. A prominent control with near-zero reach usually means a gate or a stale event mapping, not that nobody uses it; say that rather than reasoning from a bad number. And before you set your number beside one from an earlier analysis, diff the two definitions and their windows line by line: "shipped" measured as completed exports over a day and a half is a different quantity from "shipped" measured as button presses over two weeks, and comparing them yields a conclusion about definitions, not about the product. Recompute under the other definition or mark the pair non-comparable — never average over the difference. Keep raw per-user rows out of the project unless the user explicitly asks, and if they do, ask whether this project is shared first; and when a cohort lens slices below a few hundred users, aggregate up or drop the lens rather than painting a number someone could trace to a person.
