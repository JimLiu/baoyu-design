---
The user has something they want to test — maybe a finding from the data-science workflow, maybe a hunch — and wants the full experiment lifecycle run with discipline: a brief rigorous enough to hand to an engineer and a data scientist, and, once it has run, a read-out honest enough to bet a roadmap on. The discipline through all of it is the same: motivation first, pre-register the baseline before you design the treatment, instrumentation as step zero when it's missing, and a read that states every rate on the population that was randomised.

Start with motivation, and don't skip it. If there's a `findings.html` (or an overlay data file with a finding-bearing view) in the project, the finding the user names becomes the motivation more or less verbatim — the insight, the implication, and the number that makes it matter. If the user is bringing a hunch or wants to brainstorm, interview them until you can write the motivation as if it were a finding: what did you observe, what's the evidence, who does it affect, and why do you believe changing this would move something; if they want divergence first, brainstorm options with them and help pick what's testable. The brief's motivation section then says plainly that the evidence is the user's hypothesis, not a measured finding. If there's an existing experiment or prototype in the codebase that the new one builds on or replaces, read its source and write down what it does, what it costs, and — crucially — whether it's measured at all. A surprising amount of what's already shipped has no analytics, and knowing that reshapes the plan.

Pre-register before you design the treatment. Define the eligible population precisely (which sessions or users would see the change, with the exact filter you'd write in SQL), query its size per day and its current rate on the outcome you care about, and write down the control mean for the primary metric — the number the control arm will produce if you change nothing. This is one query against the analytics source (read the project's telemetry map — `telemetry-map.md`, or an older template's `metrics.skill.md` — for the table and recipe; ask the user to connect the connector if it isn't). Do it now, from live data, and cite the query job and the window. Designing the treatment first and backfilling the baseline afterward is how experiments end up unpowered or measuring the wrong population; pulling the control mean first tells you whether the effect you're hoping for is even detectable, and sometimes it tells you the experiment isn't worth running.

If the primary metric — or the surface you're changing — isn't instrumented today, that's step zero and it goes in the brief as its own deliverable. Write exactly which events are missing, what they should fire on and with what properties, and say plainly that the experiment can't start until they've shipped and accumulated a few days of baseline. This is not a blocker you bury in risks; it's the first thing the engineer does, and often it's the cheapest part.

Then write the brief. The hypothesis is one sentence: if we change X for population Y, metric Z moves from A toward B because <mechanism>. The change is described concretely enough to build — what renders, where, when it triggers, what each interaction does — and mocked on the product template as variant artboards so a reviewer can look at control and treatment side by side. Multiple directions are welcome: two or three variant options with the tradeoff each one tests, for the user to pick from or keep as experiment arms. The primary metric names the event, the baseline you just measured, the target, and the minimum detectable effect you're powering for. Guardrails are the metrics that must not get worse (error rate, latency, the north star) and the threshold at which you'd stop. Cohort and exposure unit say who's randomised and at what grain (account, org, session), which strata you'll split by, and who's excluded. Duration says how long at what split to reach power, given the eligible-per-day and control mean you measured — a rough estimate is enough here, a data scientist will refine it. Risks say what could confound it, what you'd do if the metric moves the wrong way, and which other in-flight changes this can't run alongside.

Spec the telemetry the variant adds. For every new event: name, when it fires, payload shape, and what question it answers. Prefer landing on existing events where the treatment routes to existing flows — a chip that opens the same file picker an existing menu opens doesn't need a new "attached" event, it needs a new "clicked" event and the existing one covers the rest. Distinguish the exposure event (eligible — both arms fire it, so you can count the population), the treatment event (shown — only the treatment arm, so you know it actually rendered), and the interaction events (clicked, dismissed — so "ignored it" and "rejected it" are different numbers). Never put user content in a payload.

Write the handoff block. Name the feature flag the variant lives behind and what already exists to reuse (same mount point, same component, same lifecycle usually means most of the treatment is already written). Split the work into what the engineer builds versus what the designer decides. Note the sequencing: which fixes have to land first because they'd confound the read (a reliability fix changes every downstream metric), and which other experiments this can't overlap with because they touch the same surface or the same metric.

The output is an experiment data file, `experiment-<slug>.js`, and a brief artboard that renders it. The file sets `window.__experiment = {asOf, motivation:{finding?, text}, existing?:{what, gap, note}, preReg:{eligible, eligiblePerDay, controlMean, window, query, note}, step0?:{events:[…], note}, spec:{hypothesis, trigger, treatment:[…], telemetry:[{ev,payload,note}]}, metrics:{primary:{ev,baseline,target,mde}, guardrails:[…]}, cohort:{unit,strata,exclude}, duration:{days,split}, risks:[…], handoff:{flag, reuse:[…], eng:[…], design:[…], sequencing:[…]}, results?:{…}}`. The artboard is a `.dc.html` that lays those sections out as a readable document — motivation, what exists today, pre-registration, step zero, hypothesis, the change (with the mocked variants rendered from the template), metrics, cohort and duration, telemetry, handoff — so someone can read it top to bottom and sign off. If the motivation came from a finding, link it by id; the chain from finding to experiment should be traceable. If the file already exists from an earlier pass, update it in place and mark what changed rather than starting a new one.

The brief is not the end of the job — reading the experiment is, and most of the ways a clean design produces a wrong conclusion live in the reading. Before you compare arms at all, test the split: build a first-exposure census (first exposure timestamp per unit, one arm per unit), count each arm exactly, and check the counts against the declared weights — the declared ones, not equal-by-assumption — with a chi-square, per period and cumulative. While you're there, write down which unit was randomised and which unit you're counting, because the two drift apart quietly. Then state every rate on the randomised denominator before any conditional cut. The moment you condition on something the treatment can influence — created a project, passed an eligibility gate, came back the next day — an arm that changes who reaches the denominator can fake a numerator win: a treatment that filters its entrants toward higher intent beats control per-entrant while losing per-exposed-user, and both numbers are computed from the same table. Check that the conditional denominator is balanced across arms first; when it isn't, the intent-to-treat number is the finding, and the conditional number is a mechanism note labeled as such.

A null is a number, not a shrug. Report every null with the minimum detectable effect at the N you actually have, and with the effect you had any right to expect — which, when the treatment moves an upstream behaviour that merely correlates with the outcome, is the upstream lift times the correlational gap, a product that is usually small. If the expected effect sits below the detectable one, the null was guaranteed before the data arrived and says nothing; say that, and say when it will start to mean something. When the experiment does move the upstream metric, the causal exchange rate is the downstream difference divided by the upstream difference, reported with its confidence interval especially when the interval is embarrassingly wide — an interval that contains both zero and the whole correlational gap means "too early", which is different from "no effect" and very different from "the correlation was causal". And count your tests: arms times metrics times frames, stated next to any p-value you quote, with a check that anything you're about to headline holds in the sibling frames you could defensibly have chosen — a p-value that survives correction in one frame and grazes significance in another is a watch-item, not a conclusion.

When the user comes back with "how did my experiment do?", run the read-out against the experiment's own pre-registration — the population, metric, and baseline it committed to, not a fresher frame that flatters the result. The sanity checks above come first (the split census, the randomised denominator), then the primary metric and guardrails, then whatever the data volunteers. Fill the experiment file's `results` slot and extend the brief artboard with a results section — the verdict in one sentence, the numbers with their queries cited, and what to do next — ship, iterate, or stop — with the reasoning visible, so the document stays the one place the experiment lives. Label every insight with how settled it is — established (survives the checks and the sibling frames), probable (survives most, one caveat named), directional (consistent signal, underpowered), or open (a question the data raised but can't answer) — and before any number in the read-out ships, re-derive it independently: a fresh query from the stated definition, not a copy from working notes; the two failing to match is the check working. Alongside the document, write the queries-and-insights handoff file — `experiment-<slug>-queries.md` — listing every query the read-out ran, each with the question it answers and the insight drawn from it, so a data scientist can re-run and audit the whole read without you. If the experiment is unreadable — the exposure event never shipped, the telemetry contradicts itself — say that plainly and early rather than substituting proxy metrics; an honest "we can't read this one" preserves the trust every later read-out spends.

Treat the numbers the way you'd want a reviewer to. Every figure in the pre-registration, the baselines, and the read-out cites its query job and the date window; a number you can't source is a number you don't write. If the eligible population turns out to be tiny or the control mean is already near ceiling, say so in the brief and recommend against running rather than dressing up an underpowered test. If the connector isn't available, the pre-registration block says "pending — connect analytics to fill" rather than carrying a guess, and you recommend not finalizing the brief until it's filled.
