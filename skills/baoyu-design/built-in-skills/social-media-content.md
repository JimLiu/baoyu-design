name: "social-media-content"
description: "Social media content\nPosts, carousels, and campaign assets — in your brand, sized for every platform, exact-size downloads"
---
The user wants social media content — a campaign, posts, carousels, or one design fanned out across platforms — delivered as ready-to-post, platform-sized assets. Whether they arrive with finished art or just an idea, the deliverable is a social-asset board: a Design Component where every format shows in realistic platform context (an iPhone for every mobile format — stories and the platform post shells — and a browser window with a real feed post for the X/LinkedIn/Facebook/Reddit desktop placements), formats toggle on and off from the product's Tweaks panel, and every frame downloads at its exact pixel size with zero shell dressing. The board is a normal .dc.html design file — everything in your Design Components authoring spec applies; this skill adds the board anatomy.

START by copying the four starters in with `copy_starter_component`: `"social_frames.js"` (the board wrapper), `"ios_shell.js"` and `"chrome_shell.js"` (the presentation shells), `"post_card.js"` (platform feed cards), plus `"image_slot.js"` if the project doesn't already have it. Load them from the DC's <helmet> with plain <script src> tags, and include <meta name="design_doc_mode" content="canvas"> there so the board sits on the pannable canvas. Each copied file opens with a USAGE block — the attribute reference when you need it.

The board: one <social-frames> element as the template's ONLY root element (a sibling heading outside it breaks the host's frame-export detection), containing one unit per format — each unit a plain <div> directly inside the wrapper (never a shell as the direct child: shells re-slot their children and would swallow the wrapper's injected label bar). Wrap each unit in <sc-if value="{{ show.<format> }}" hint-placeholder-val="{{ true }}">, expose the matching boolean props (default true) under `"section": "Formats"` in the props metadata — name each prop EXACTLY as the platform/asset reads in the panel (`instagramPost`, `instagramPortrait`, `story`, `xPost`, `facebook`, `linkedin`, `pinterest`, `reddit`, `youtubeThumbnail`, `tiktok`, `xDesktop`, `linkedinDesktop`, `facebookDesktop`, `redditDesktop`), never a show/display prefix — the key IS the visible label and the toggle is self-explanatory, and return the show map from renderVals — that is the whole toggle mechanism; the Tweaks panel renders the Formats section itself. Also expose one `imagesOnly` boolean (default false, `"section": "Display"`) and bind image-only="{{ imagesOnly }}" on EVERY shell element on the board — all semantic shells including <instagram-story> and <tiktok-shell>, and every <chrome-shell> and <post-card> — never just one of them; a board where only some units respond to the toggle is broken — that is the "[images only / product shells]" tweak: on, everything strips to just the assets (the story keeps its exact frame size, only the bezel dressing goes); exports are identical in both modes. Don't build any in-page controls, download buttons, or export methods in the logic class: the wrapper injects a label bar and exact-size "↓ PNG" button on every unit, one "Download all (zip)" toolbar, and all the export wiring, and it re-numbers correctly as formats toggle.

Be exhaustive by default: unless the user names specific formats, the board carries the full default roster — ten mobile units (`instagramPost`, `instagramPortrait`, `story`, `xPost`, `facebook`, `linkedin`, `pinterest`, `reddit`, `youtubeThumbnail`, `tiktok`) AND four desktop placements (`xDesktop`, `linkedinDesktop`, `facebookDesktop`, `redditDesktop`), fourteen units in all — so nothing has to be asked for twice; the Formats toggles are how the user narrows. When the user DOES name platforms, a named platform means both its mobile shell and its desktop placement (where one exists) unless they say mobile-only. Inside each unit, compose the context — and for mobile social formats, NEVER hand-build platform chrome: use the semantic shells, which render a complete, pre-designed app screen from attributes alone. <instagram-shell image-src="…" username="…" caption="…" likes="…" aspect="square|portrait">, <reddit-shell community="…" title="…" upvotes="…">, <x-shell name="…" handle="…" text="…">, <facebook-shell name="…" text="…">, <linkedin-shell name="…" headline="…" text="…">, <pinterest-shell title="…" username="…">, <youtube-shell title="…" channel="…" views="…" duration="…">: copy those starters in (each composes ios_shell.js itself), give each element an id (the embedded image-slot's persistence id derives from it), fill the attributes with real campaign copy in the platform's voice, and the export frame comes baked in — right label, right aspect, drop-and-replace photo. Stories are a semantic shell too — <instagram-story id="…" image-src="…" username="…" avatar-src="…" time="…" image-only="{{ imagesOnly }}"> renders a complete story-viewer screen (progress segments, avatar header, "Send message" reply bar, all export-hidden) with the story canvas letterboxed at 9:16 on black inside the same uniform phone, export frame and label baked in; copy instagram_story.js in alongside the other shells and never hand-build story chrome or author a bare <ios-shell> story unit. TikTok is the same pattern — <tiktok-shell id="…" image-src="…" username="…" avatar-src="…" caption="…" sound="…" likes="…" comments="…" saves="…" shares="…" image-only="{{ imagesOnly }}"> renders a complete For-You video screen (Following/For You tabs, right-rail action stack, caption + sound rows, bottom nav, all export-hidden) with the video canvas letterboxed at 9:16 inside the same uniform phone, export frame and label baked in ("TikTok · 1080×1920"); copy tiktok_shell.js in alongside and never hand-build short-video chrome. Overlays (headline plates, scrims, stickers) go in as <instagram-story> children — they land inside the story canvas. Size overlay text relative to the frame's RENDERED width (the on-screen frame is ~400px, not 1080 — a 1080-canvas font size will overflow), and make scrims/text overlays pointer-events:none (re-enable on interactive children) so the photo's hover controls stay reachable. Desktop feeds — one unit each for `xDesktop`, `linkedinDesktop`, `facebookDesktop`, `redditDesktop`: a <chrome-shell tab="…" url="…"> around a <post-card platform="x|linkedin|facebook|reddit" name="…" sub="…" text="…">, with your export frame as the post-card's child (it becomes the card's media). These units are why you copied chrome_shell.js and post_card.js — load both from <helmet> with the other starters, or the desktop units render bare (no window, no card). The export frame is the one element per unit carrying data-om-frame-export="" and data-om-frame-label="<Label> · <W>×<H>" — sized with aspect-ratio in the layout to EXACTLY the label's W:H ratio (it can render small — exports upscale to the label's nominal W×H, so an off-aspect frame ships a distorted asset, and platforms reject off-spec files; a frame filling an <ios-shell> screen is exact when screen-height = screen width × H/W). Standard sizes: Instagram post 1080×1080, portrait 1080×1350, story 1080×1920, TikTok 1080×1920, X 1200×675, LinkedIn 1200×627, Facebook 1200×630, Reddit 1200×675, YouTube thumbnail 1280×720, Pinterest 1000×1500; desktop placements reuse their platform's asset size (xDesktop 1200×675, linkedinDesktop 1200×627, facebookDesktop 1200×630, redditDesktop 1200×675 — the browser window is context, not part of the asset); any custom size is just another unit with its own label.

You have total creative control inside each frame: an <image-slot> for the user's droppable photo plus designed overlays (scrims, brand marks, typographic headlines — use the project's bound design system fonts), or a fully designed composition, per format rather than one layout squashed across ratios. HARD REQUIREMENT: give every <image-slot> a distinct id — drops persist by slot id, which is exactly what makes a user's dropped photo survive a format being toggled off and back on. Shell dressing that overlaps a frame (the phone's status bar over a story) is already export-chrome-marked by the shells; anything you author that overlaps a frame but must not ship in the asset gets data-omelette-chrome.

Which formats: if the user named platforms, build those (desktop placements included, as above). If the brief doesn't say, ask once with a question page — build it from the svg-options pattern and show it with ask_user_page — each option drawn as a proportional rectangle labeled with its dimensions, where every roster unit appears in the menu — grouping related units into one option is fine (e.g. the four desktop placements as one "Desktop feeds" option at a representative size), omitting a unit is not, and reddit in particular must appear — and state the default as that full fourteen-unit roster so they can just say "go". "Go", a skipped or unanswered formats question, or an interrupted round all mean build all fourteen — never a mobile-only subset. Never hide a frame with display:none or visibility:hidden, and never put sc-if INSIDE a shell — formats toggle as whole units through sc-if, which keeps the download numbering honest and the shells' one-time child slotting intact. Per-frame downloads need at least two visible formats (the wrapper hides the buttons below that; the zip toolbar too). Downloads are built in; never screenshot frames yourself.

Treat the content as marketing work, not placeholder filler: if the brief doesn't say, fold WHAT the campaign is about and any brand constraints (colors, fonts, assets, voice — or none, in which case offer 2–3 distinct visual directions) into the same single questions round as the format picker — never a second interview. Copy discipline for everything you write into the cards and frames: short, specific, in each platform's idiom, drawn from the user's actual material — no hashtag walls, no generic engagement bait, no caption that could sit under anyone's post.

When the user wants a carousel, it is a narrative, not a pile of slides: 5–10 frames with an arc — a hook frame that earns the swipe, content frames that each carry exactly one point, a closing call-to-action frame — all sharing one visual system (same type scale, palette, margins) so the set reads as one piece. Build it as carousel frames on the same board (Instagram portrait units work well) so the whole set downloads at platform size like everything else, and give the carousel ONE boolean in the Formats section toggling the whole set — not a toggle per frame.
