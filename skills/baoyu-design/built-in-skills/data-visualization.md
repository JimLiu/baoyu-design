name: "data-visualization"
description: "Data visualization\nCharts, graphs, and dashboards from your data — interactive d3 with zoom, tooltips, and image download"
---
The user wants to see their data, not read it — the deliverable is an interactive d3 visualization: a plain .html project file built on the chart_stage.js starter, where they can zoom into the detail, hover or tap any mark for the exact values behind it, resize without anything breaking, and download the result as an image. Getting there has three beats: get data in hand, agree on what to look at, then build it well.

FIRST, the data. Check what already exists before asking: files attached to the message or sitting in the project (`read_file` for CSV, TSV, or JSON; `run_script` to parse or aggregate anything big), and connector tools in your tool list from the user's connected apps (they arrive named `{app}__{tool}` — Google Drive, Notion, whatever the user has connected; offer and use a connected source by name only when its tools are actually present). If there is nothing to plot yet, ask ONCE with a question page built from the select or text-options pattern (the "Ask the user" skill has the details), its options the source choices — each available connected app, "I'll attach a file", "I'll paste it", "Start with sample data (swap in real data later)" — shown with ask_user_page. Data files ride chat or the project, not the page — skip the upload pattern for this ask: the page's prompt (and your chat line) should say to attach the file to their next message or drop it into the project's files — CSV, TSV, or JSON; Excel can't be read here, so ask for a CSV export when a spreadsheet is likely. A skipped round, a "Decide for me", or a sample-data answer means: fabricate a realistic dataset shaped to the ask — plausible values and names, trend, seasonality, a couple of honest outliers — and say plainly in chat that the chart is running on sample data. Either way, put the rows in their own `data.js` that assigns `window.__data` (the chart file stays data-agnostic, and real data later drops into the same columns), and read enough of what arrived to know its true shape before proposing anything: row count, columns and their types, ranges, what's missing. Never re-ask for something you already have.

SECOND, the options round — the chart follows the question, not the data. Name what the user wants to SEE — change, comparison, composition, distribution, relationship, flow — and the family is mostly decided: change over time → a line per series (an area only when cumulative magnitude is the point); comparison across categories → horizontal bars, sorted by value (alphabetical is a sort nobody chose; keep a natural order only when the categories have one); part-of-whole → stacked bars, or a treemap when the parts nest; distribution → histogram (box plots only to compare distributions across groups); relationship between two measures → scatter (size for a third, a heatmap when both axes are categorical); flow between states → sankey. Past about six series, never spaghetti: small multiples, or one highlighted series over gray context. Two anti-defaults that earn their place: no pie chart unless share-of-one-whole with five or fewer slices is truly the question (angles compare worse than lengths — a sorted bar answers the same question faster), and never a dual y-axis (two scales on one panel manufacture correlation; use two panels sharing an x-axis).

When the user named the chart they want, build that — no options round. Otherwise ask once with an options page built from the svg-options pattern — 2–4 candidates, each option's thumbnail a low-fi inline-SVG sketch of THIS data in that family — a dozen hand-placed shapes suggesting the actual pattern (the real trend direction, the true number of categories, the actual skew), not a generic chart icon — each option's description naming at equal depth which question it answers best and what it gives up — and show it with ask_user_page. The candidates must differ on one nameable axis: different questions answered (trend vs distribution), or one genuinely contested design decision (zero-baseline vs zoomed-in y, daily vs weekly bins) — never four shades of the same idea. Scale, baseline, bin width, aggregation grain, outlier handling, and color encoding change the story a reader walks away with, so they are design decisions the user may legitimately want different — when one is contested for this data, it can BE the axis an option pair differs on; otherwise pick the defensible default and say it in one line when you present ("y starts at zero; weekly bins; two points beyond p99 excluded"), so the user objects to a decision instead of discovering it. Fold anything else you genuinely need into the same page as its own section (a freeform ask if it is open-ended) — never a second interview — and state the default in the page so a skip or "Decide for me" just means you build the best candidate and say which decisions you made.

THIRD, the build. The chart page is plain HTML — a .html file with ordinary <script> tags, NEVER a .dc.html Design Component, even when every other design in the project is one: DC confines scripts to <helmet>, whose mount timing fights a stage shell, and its runtime pulls in React that a d3 chart never needs — the same call the 3D skill makes. START by calling copy_starter_component with kind: "chart_stage.js" — the stage owns the chart chrome (container-driven resize, wheel/drag/pinch zoom and pan with a reset control, a mouse-and-touch tooltip, labeled empty and error states, data transitions, PNG/SVG downloads); you write only the draw function, against the contract in the copied file's usage block. A dashboard is several chart-stage elements composed on one page: shared data.js, a heading and layout you design, each stage with its own name and a zoom mode fitted to its chart. Load d3 ONLY through these exact pinned, hash-verified tags, in <head>, before chart-stage.js — do not change versions, URLs, or hashes, do not add other copies of d3, and include the sankey tag only when the chart uses it. These two tags are hash-verified and fail closed if tampered with; any other script you add would load unverified — so add nothing else from a CDN:

<script src="https://unpkg.com/d3@7.9.0/dist/d3.min.js" integrity="sha384-CjloA8y00+1SDAUkjs099PVfnY2KmDC2BZnws9kh8D/lX1s46w6EPhpXdqMfjK6i" crossorigin="anonymous"></script>
<script src="https://unpkg.com/d3-sankey@0.12.3/dist/d3-sankey.min.js" integrity="sha384-SM54CE5h+qdDI046d2Y5ym7wq1kq4uxcQ1cqGq5/+5jrE5tPLeDJSq711Q8sIska" crossorigin="anonymous"></script>

Set the stage's zoom attribute deliberately — "x" for time series (zoom into a date range), "y" for horizontal bars, "xy" for scatters, "none" for treemaps and pies where panning is meaningless. When a range is the real control, use a brush instead of zoom, not on top of it — a d3.brush and the stage's whole-svg zoom fight over the same drag, and the brush doesn't track zoom state: set zoom="none" and let a context strip's brush drive the main panel's domain through stage.refresh(). Inside the draw function, hold the craft the stage can't do for you: axes labeled with units, tick values formatted for reading (12k not 12000; dates at the data's grain); series labeled directly at the line's end where they fit, a legend only where direct labels genuinely don't; tooltips giving the exact values, including anything an axis truncated (a tooltip renders as plain text unless you return { html } — then escape every data string you didn't author with the stage's esc helper); missing values rendered as gaps, never as zeros — a zero is a claim, a gap is honest; long category labels wrapped or truncated with the full text in the tooltip; thousands of points aggregated or thinned before the DOM dies doing it for you (bin a dense scatter into a density/hex view above roughly five thousand points, downsample a long series to what a pixel can show). A bar chart's baseline is zero, always — length IS the encoding, so a truncated bar is a lie; a line chart may zoom, said out loud. Color encodes in matched type: a sequential ramp for ordered values, a diverging ramp around a meaningful midpoint for signed ones, distinct hues for at most seven unordered categories — past seven it is not a color scale, it is a legend nobody can read.

The chart is product surface, so it wears the project's design system when one is bound: link the design system's stylesheet into the page and set the stage's custom properties (--chart-font, --chart-ink, --chart-muted, --chart-surface, --chart-grid) from its tokens, use its type for titles and axes, and draw series color from its palette — if the design system defines chart tokens (a categorical series palette, sequential and diverging ramps, status colors, grid/axis ink), use those directly for the matching scale type; otherwise build the ramps from its accent and neutrals. No design system bound means restrained defaults with the same structure: one accent for single-series ink, neutral grays for grid and axis, color spent only on data.

Then look at what you built: screenshot the rendered page and check it like a reviewer — labels not overlapping, axes readable at the rendered size, the empty state wired (try the chart with zero rows once), the sorted order right, nothing clipped. Present the finished chart with the one-line decisions note, what the sample data is standing in for when it is, and the one or two adjustments you'd most expect ("want this weekly instead?", "log scale?") — then stop; don't rebuild unasked.
